§ 2Rectified flow in five minutes

Everything in model.py follows from one equation. Understand this section and the rest of the file is bookkeeping.

2.1 · The single idea

Take a real image and call it x₀. Take pure Gaussian noise and call it x₁. Now draw a straight line between them and put a dot somewhere on that line. The dot's position is described by one number, t:

xt = (1 − t)·x0 + t·x1 with t = 0 → clean image,   t = 1 → pure noise

That is the entire "forward process". There is no gradual noise schedule, no Markov chain, no β-parameters — just a line segment. The model's whole job is to learn the velocity: the direction and speed you would have to travel along that line. Formally it learns the vector field

v(xt, t) = dxtdt = x1 − x0

Notice what that means: the target the network is trained to predict is simply noise minus image. Not the noise, not the clean image — the difference. This is why FLUX.2 is called a flow model rather than a diffusion model: it is trained to integrate an ordinary differential equation along (approximately) straight paths, following Lipman et al. 2023 and Liu et al. 2023.

2.2 · Reading the sampling step

With that picture in mind, the denoising loop in sampling.py is three lines:

guidance_vec = torch.full((img.shape[0],), guidance, device=img.device, dtype=img.dtype) for t_curr, t_prev in zip(timesteps[:-1], timesteps[1:]): t_vec = torch.full((img.shape[0],), t_curr, dtype=img.dtype, device=img.device) ... pred = model(x=img_input, x_ids=img_input_ids, timesteps=t_vec, ctx=txt, ctx_ids=txt_ids, guidance=guidance_vec) ... img = img + (t_prev - t_curr) * pred # <-- the only line that changes the image return img

The img = img + … line — sampling.py:305 — is exactly the pink arrow in FIG 2. t_curr is where we are, t_prev is where we want to be next (always a smaller number), pred is the velocity v that Flux2.forward just returned. Multiplying velocity by the time difference gives the displacement. Nothing else happens — no noise is injected, no variance schedule is applied. It is a plain, deterministic Euler integration of an ODE.

💡 Two questions this loop always raises

Which of the two times does the model get — the start or the end of the interval? The start: t_curr, the noisier end. sampling.py L285 fills a vector with t_curr and L297 passes it as timesteps, and the other two loops do the same (L329/L335, L384/L395). That is exactly what an explicit Euler step means — evaluate the velocity field where you are standing, then travel; evaluating it at the destination would require already knowing the destination. So an 8-step run makes 8 calls, at t = 1.000, 0.985, 0.967, 0.942, 0.906, 0.853, 0.763 and 0.580. The schedule's ninth entry, 0.0, is only ever a destination and is never fed to the network (§15.1 prints both rows).

And how does the model know the step size, t_prev − t_curr? It does not, and it never needs to. Its signature is forward(x, x_ids, timesteps, ctx, ctx_ids, guidance) — no step size, no schedule, no num_steps, and none of those three words appears anywhere in the 833 lines. The network answers a purely local question — "at this x and this t, which way does the trajectory point, and how fast?" — while the sampler owns the global plan: get_schedule produced all N+1 times before the loop began, so the step size is just the difference of two numbers already in hand. That division of labour is why one set of weights serves a 4-step, an 8-step and a 50-step run unchanged: nothing in the model knows how far it is being asked to travel, it only ever says which way.

⚠ Gotcha · which direction is "forward"?

The convention here is t = 1 is noise and t = 0 is data — the opposite of what many diffusion tutorials use, where t counts up as noise is added. In this codebase get_schedule returns timesteps starting at 1.0 and ending at 0.0, and the Euler step moves down. Keep that in mind whenever you see a timestep value: big = noisy, small = clean.

2.3 · The timestep schedule is not uniform

If you split [1, 0] into 50 equal slices you waste steps in the easy middle of the trajectory and starve the hard part. Which part is hard? Empirically, the noisy end: deciding the global composition from near-pure noise is where most of the information is created, and it is also where the velocity field curves the most. So FLUX.2 warps the uniform grid through a shift function, taken from the Stable Diffusion 3 paper:

t′ = eμeμ + (1/t − 1)σ μ = f(number of tokens, number of steps), σ = 1

💡 Why this matters for reading the code

model.py never sees the schedule; it only ever receives one value of t per call, via the argument named timesteps. So whenever you read "timestep" in this file, think: "a single float telling the model how noisy its input currently is". Because of the shift above, that float spends most of the run in a narrow band near 1 — 39 of the 50 steps at 1 MP sit above t = 0.7 — so the model has to resolve very fine differences inside it, which is one more reason the scalar is expanded into 128 frequencies (§8.1) rather than fed in raw. The × 1000 inside timestep_embedding is a separate matter: a scale convention, not a consequence of the schedule.

2.4 · One more input: what "guidance" actually is

The loop above passes the model four things — noisy latents, their position ids, the timestep, the text — and for some checkpoints a fifth: guidance. It is one number, and the file never explains it, so here it is. It matters twice: it is the second "setting" that §7 routes into the network, and it is a config field in §6 (use_guidance_embed).

The problem. A model trained to follow a prompt follows it politely. It produces something consistent with the words but hedged — washed out, under-committed, averaging over everything the prompt could have meant. Classifier-free guidance (Ho & Salimans, 2022 — §18) is the classic fix: run the network twice per step, once with the prompt and once with an empty one, and extrapolate past the conditional prediction.

Σ Classifier-free guidance, one step

v = v_uncond + w · (v_cond − v_uncond)

w = 1 → the plain conditional prediction · w > 1 → step further along "what the prompt changes" · w = 0 → ignore the prompt

The bracket is exactly what the prompt changes, so multiplying it by w > 1 amplifies only that. It works — and it doubles the cost: 100 network evaluations for a 50-step image.

What FLUX.2 does instead. use_guidance_embed says whether the model takes w as an input. Where it does, the value is fingerprinted and embedded exactly like the timestep and added to the same condition vector (§7.5), so a single pass approximates what the two-pass extrapolation would have produced — the model was trained to reproduce it, which is what "guidance distillation" means. The dev configuration sets use_guidance_embed=True and util.py drives it with guidance=4.0 over 50 steps. Both klein configurations set it to False: those networks have no guidance input at all, and util.py accordingly runs them with guidance=1.0 — no amplification — in 4 steps.

sampling.py still carries the two-pass version as its own entry point (denoise_cfg): it duplicates the batch, passes guidance=None to the model, and combines the two predictions outside the network. Same idea, no distilled input, twice the compute.

⚠ Do not confuse the two

A distilled guidance value — this file's guidance_in — is one scalar fed into one forward pass. True classifier-free guidance is two forward passes combined afterwards. Nothing in model.py ever does the second: the file only sees the scalar.

§ 3From pixels to tokens: what the model actually eats

model.py has no convolutions and no image logic. It receives images that have already been flattened into a list of vectors. To understand its shapes you must know exactly how that flattening happens.

3.1 · Three stages of compression

Two of the three stages happen inside the VAE, in autoencoder.py's encode(): the convolutional 8× downsample to 32 channels, and the 2×2 patchify that folds four latent cells into one 128-number token. The third — flattening that 2-D grid of tokens into a plain sequence and attaching the position ids — is sampling.py's prc_img, run just before the model is called:

◇ Beginner · why bother with latents at all?

Attention costs grow with the square of the token count. A 1024×1024 image as raw pixels would be over a million tokens: 10¹² attention pairs per layer, utterly impossible. As 4096 tokens it is 21 million pairs — expensive but feasible on real hardware. The latent space is a compression scheme that throws away perceptually irrelevant detail (exact sub-pixel noise) while keeping everything a human would notice. One detail worth knowing, because it explains a shape you will see in autoencoder.py: the 128-channel latent is normalised by a running-statistics BatchNorm2d(128, affine=False, eps=1e-4) inside the autoencoder (autoencoder.py L293–325) — no per-channel scale/shift factors for the transformer to carry around.

The 512 text tokens do not grow, so the joint sequence goes 4608 → 16 896, a factor of 3.7, and attention work, which is quadratic in that joint length, by 13.4×. That single fact explains most of FLUX.2's engineering: the KV cache for references (§14), the shared modulation (§16), and the choice of 48 cheap single-stream blocks over expensive double-stream ones.

3.3 · Text tokens, and the mystery of 15360

The text side is simpler but has one surprise. The 24-billion-parameter Mistral VLM is run over your prompt, and then three of its internal layers — layers 10, 20 and 30 — are pulled out and stacked side by side:

OUTPUT_LAYERS_MISTRAL = [10, 20, 30] # which VLM layers to read out = torch.stack([output.hidden_states[k] for k in OUTPUT_LAYERS_MISTRAL], dim=1) return rearrange(out, "b c l d -> b l (c d)") # (B, 512, 3*5120) = (B, 512, 15360)

Mistral-Small-3.2 has a hidden width of 5120, so each prompt token arrives as 3 × 5120 = 15360 numbers. That is precisely Flux2Params.context_in_dim. And the reason the Klein configs use 12288 and 7680 is exactly the same trick with different teachers: Qwen3-8B (4096 × 3) and Qwen3-4B (2560 × 3). Using mid-depth layers rather than only the last one gives the flow transformer access to both syntactic and semantic features — a trick also used in SD3.

Prompts are padded and truncated to MAX_LENGTH = 512 tokens, which is where the "512 text tokens" column above comes from.

3.4 · Reference images are just more tokens

For editing and multi-reference generation, reference images go through the same VAE encoder and the same patchify, and their tokens are simply appended to the sequence. Up to ten references are supported; to keep the cost sane the pipeline caps reference pixels at 1024² each when there are several, and 2024² when there is only one (sampling.py L56–58 spells it 2024**2, which is what upstream says — almost certainly a typo for 2048²). The only thing that distinguishes a reference token from a canvas token is its position id — which is the subject of §5.
