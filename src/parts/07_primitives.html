8.1 · timestep_embedding(t, dim, max_period, time_factor) — L710

The model needs to know how noisy its input is. But a single float like 0.87 is a terrible input for a neural network: one number cannot be meaningfully multiplied by a 6144-column weight matrix in a way that distinguishes 0.87 from 0.86. The standard fix, inherited from the original diffusion paper and from Transformers' positional encoding, is to expand the scalar into a bundle of sines and cosines at many different frequencies.

∑ The formula in one line

emb(t)[2i] = cos( 1000·t · 10000^(−2i/dim) )
emb(t)[2i+1] = sin( 1000·t · 10000^(−2i/dim) )

128 frequencies spanning four orders of magnitude means the embedding changes fast in some coordinates and slow in others — so a linear layer reading it can resolve both "roughly how noisy" and "exactly how noisy".

Used later: MLPEmbedder (§8.3) turns this code into the condition vector.

8.2 · SiLUActivation — L390

Despite the name, this is not just an activation function: it is a gate, and it halves the width of whatever you give it.

That is also why every MLP input layer in this file produces twice its nominal width. The factor is stored rather than written out — self.mlp_mult_factor = 2 at L451 (single block) and L538 (double block) — and then appears in four width expressions: mlp_hidden_dim * self.mlp_mult_factor at L455 and L474 (the fused linear1 and the torch.split that undoes it) and at L547 and L562 (the two streams' MLPs). Half of those columns are the gate, and they will be consumed by this multiplication.

Used later: every block MLP (§10–§11) — and nowhere else. MLPEmbedder (§8.3) and Modulation (§8.9) use a plain SiLU — nn.SiLU() in one, nn.functional.silu in the other — with no gate and no halving.

8.3 · MLPEmbedder — L683

The sinusoidal fingerprint is still just a fixed code; the model needs to learn what to do with it. MLPEmbedder is the smallest possible learned transformer of a vector: two linear layers with a nonlinearity between them.

In Flux2 this class is instantiated twice: as time_in for the noise level and, when use_guidance_embed is set, as guidance_in for the guidance strength. Their outputs are simply added, so both signals share every downstream modulation weight.

Used later: Flux2 builds time_in and guidance_in from this class (§12).

8.4 · rope — L818

rope is the factory that manufactures the 2×2 rotation matrices of §5.1 from raw position numbers — honestly the densest eight lines in the file, so we will take them extremely slowly. In: a tensor pos of shape (B, L) holding one axis's coordinate for every token, a dimension budget dim (32 for each FLUX.2 axis) and the base theta. Out: (B, L, dim/2, 2, 2) — one genuine rotation matrix per rotation plane per token.

Used later: EmbedND (§8.5) calls it once per position axis.

8.5 · EmbedND — L694

Every token that enters FLUX.2 carries a small address: four numbers, one per position axis (§5). EmbedND is the machine that turns those addresses into something attention can actually use — a stack of rotation matrices, one per rotation plane of the head. It owns no parameters at all: no weights, no tables, just trigonometry, recomputed from scratch on every call.

What goes in

One tensor, ids, of shape (B, L, 4): a batch of L tokens, each with its four integer coordinates. (sampling.py builds them with torch.cartesian_prod over torch.arange, so they arrive as int64; rope multiplies them by a float32 frequency ladder, which is where they become angles.) Concretely, a row looks like this:

tokenthwlwhy
a canvas token at row 17, column 42017420the image being drawn lives at t = 0; text slot unused
the same pixel of reference image #33017420references sit ten t-units apart: 10, 20, 30…
the 6th word of the prompt0005text has no pixels: t, h, w are dummies, l sweeps the sentence

The constructor also takes three settings: dim = 128 (the head width — stored, and then never used again; the real budget comes from axes_dim), theta = 2000 (the frequency base), and axes_dim = [32, 32, 32, 32] — how many of the 128 head dimensions each axis owns.

What happens inside — four slices, four ropes, one glue

Step 1 — slice off one column. ids[..., i] takes axis i's coordinate for every token at once: a (B, L) tensor of plain positions. For i = 1 that is the list of all row numbers; for i = 3 the list of word indices.

Step 2 — rope that column. Each slice is handed to rope (§8.4) together with that axis's dimension budget, axes_dim[i] = 32. rope pairs those 32 dimensions into 16 rotation planes and writes one 2×2 rotation matrix per plane per token — the matrix from §5.1, with angle position × ω of that plane. Output per axis: (B, L, 16, 2, 2) = batch × token × plane × 2×2 matrix.

Step 3 — glue the four bundles together. torch.cat([...], dim=-3) stacks the four bundles of planes end-to-end along the plane axis: 16 + 16 + 16 + 16 = 64 planes, giving (B, L, 64, 2, 2). Why dim=-3? Count axes from the right: −1 is the matrix column, −2 the matrix row, −3 the plane. Concatenating at −3 leaves every 2×2 matrix untouched and simply lines the planes up in axis order — t's 16 planes first, then h's, then w's, then l's. That order is a contract: plane j of this output is exactly the rotation that apply_rope will apply to dimensions (2j, 2j+1) of q and k, which is precisely the dim-split drawn in FIG 8.

Step 4 — make room for heads. unsqueeze(1) inserts a size-1 axis at position 1: (B, 1, L, 64, 2, 2). All 48 heads of a layer share the same rotations, so a size-1 axis lets one computed copy broadcast across every head for free during apply_rope — the rotations are computed once per token, not once per token per head.

Used later: every block feeds this output to apply_rope (§8.6).

8.6 · apply_rope — L828

rope built the rotations; apply_rope is the small consumer that actually turns q and k with them. In: a query or key tensor of shape (B, H, L, 128) and the rotation stack freqs_cis of shape (B, 1, L, 64, 2, 2) — exactly what EmbedND returned in §8.5, its size-1 head axis broadcasting over all heads. Out: the same shape as the input, every adjacent pair of dimensions rotated, computed in float32 and cast back.

⚠ Gotcha · queries and keys rotate, values do not

Look at the four places apply_rope is called — L496 and L518 in the single block's two forwards, L649 and L675 in the double block's two forwards: it is always applied to q, k only. That is correct and important. Position information must live in the comparison between a query and a key; rotating the values too would rotate the information being retrieved, which is not what you want. The relative-distance trick from §5.1 works precisely because q and k are rotated identically.

Used later: all four attention sites inside the blocks (§10–§11).

8.7 · RMSNorm and QKNorm — L734, L746

Attention scores are dot products of queries and keys. During training those vectors can grow large, and a few oversized keys can dominate every softmax in the layer — a well-known instability. The fix used here — normalise queries and keys per head before the dot product — is Henry et al.'s query-key normalisation, which SD3 and FLUX.1 also use; the root-mean-square statistic it is computed with is Zhang & Sennrich's RMSNorm.

Across the whole 32B model there are 128 RMSNorm modules — one q and one k per attention — and their 16,384 scale values are the only parameters in the file that are not part of a matrix multiply.

Used later: SelfAttention (§8.8) owns one QKNorm per attention bundle.

8.8 · SelfAttention — L375

Now for something genuinely surprising. Read the whole class:

There is no forward method. You cannot call self.img_attn(x) — Python would raise NotImplementedError from nn.Module's fallback. SelfAttention is used purely as a container of parameters: the fused QKV projection, the QK normalisation, and the output projection. The actual attention mathematics lives elsewhere: the blocks of §10–§11 read .qkv and .norm directly, the attention routine of §9 does the softmax, and .proj finishes the result inside the blocks' residual step.

💡 Why write a class with no forward?

Honest answer: it groups the four attention parameters under one name so that block.img_attn.qkv.weight reads clearly and so checkpoint keys stay tidy, while letting the block control exactly how and when each piece is used. FLUX.2's blocks need to interleave attention with modulation, RoPE and the reference routing of §9, so a rigid forward(x) → x would not fit anyway. It is a pragmatic choice, and once you know it the file stops being confusing: whenever you see self.X_attn. followed by a member name, you are looking at parameter access, not a call.

Used later: each block owns one of these per stream (§10–§11).

8.9 · Modulation — L400

This is the class that gives the timestep its hands: stage 4 of §7.5, the matrix that turns one condition vector into everybody's shift, scale and gate. The technique is adaptive layer normalisation (adaLN), from the DiT paper, and §7.3–§7.4 built the idea from nothing — why a normalisation layer is the place to inject, what the three dials do, and what the 1 + is for. What is left here is the plumbing, and the plumbing is worth reading closely, because 13 lines decide the shapes that all 56 blocks consume and one of them is a tuple convention that reads like a bug.

The same thirteen lines again, this time as a shape trace — the column on the right is what the blocks in §10 and §11 actually receive:

Chunk order is fixed by the consumers, not by this class: shift, scale, gate — and for a double=True module (L401–405), the attention triple first and the MLP triple second. That is the order L469 unpacks in a single block (mod_shift, mod_scale, mod_gate = mod) and the order a double block unpacks in two stages: into img_mod1, img_mod2 = mod_img at L570, then each of those into its own three at L573–576. Nothing in the file enforces any of it. Change the order here and every block silently applies a gate where a shift belongs.

◇ One timestep, end to end

Take t = 0.62 in a dev run with guidance = 4.0. §8.1 turns the scalar into 256 numbers between −1 and 1; §8.3 turns those into vec, 6144 numbers; the guidance value takes the same two steps through its own copy and is added in (L130). Now this class applies SiLU to those 6144 numbers, multiplies by a 6144 × 36 864 matrix, and slices the result into six vectors of 6144. Double block 0 takes the first three: img_mod1_scale and img_mod1_shift are multiplied and added into the normalised image tokens at L580, and img_mod1_gate scales that block's attention output before it lands in the residual stream at L626. Blocks 1–7 receive the same six vectors — this class ran once for the whole stack. Across a 50-step run the entire conditioning mechanism is 50 × 3 matrix products, against 50 × 56 blocks of real work.

Three modules are built, at L98–108, and the call sites are worth seeing together because they show exactly what is shared and what is not:

Two details in that table are the whole of §13 in advance. First, double_stream_modulation_txt has no reference call: the text stream contains no reference tokens, so its dials can stay one broadcast value per step. Second, _img and single_stream_modulation are each called twice in forward_kv_extract — once with vec (the real timestep) and once with ref_vec (a timestep pinned to 0.0) — because a broadcast dial cannot say "these 16 384 tokens are clean and the rest are not". Splicing the two results is what the three _blend_* functions do.

And one absence: bias=False. A bias on this matrix would be a constant added to every dial, but shift is already an additive dial, so a bias could only ever be absorbed into it — redundant parameters with no extra expressiveness. That is the file-wide rule of §1.1 (zero biases in 171 linear layers) showing up in the one place where a bias would have been most defensible.

Used later: Flux2 builds the three modules at L98–108 and calls them at L132–134, L206–211 and L290–292 (§12); every block consumes their triples (§10–§11); §13 splices two runs of them together for the reference tokens.

8.10 · LastLayer — L415

The exit door. It must turn 6144-dim hidden states back into 128-dim latent tokens, and it gets one final chance to let the timestep modulate the result.

◇ Beginner · recap of section 8

You now hold every tool the big blocks use, in the order they were built: a sinusoidal time code (timestep_embedding), the gate (SiLUActivation), the learned conditioner (MLPEmbedder), the position factory (rope), the four-axis assembler (EmbedND), the rotation applicator (apply_rope), the stability norms (RMSNorm, QKNorm), the attention parameter bundle (SelfAttention), the timestep's dials (Modulation) and the exit projection (LastLayer). Every one of them was explained before anything that uses it. From here on, nothing new is introduced — only combined.
