§ 4Position: the four-axis rotary embedding

§3 ended on attention's blind spot: a dot product cannot see order. Feed the same tokens shuffled and the scores shuffle with them — nothing in the mechanism knows which token came first, or which patch sits next to which. Everything spatial about an image, and everything sequential about a sentence, must be injected deliberately, into q and k, before attention runs. FLUX.2 does it with RoPE, extended to four axes at once.

4.1 · RoPE in one paragraph — and three pictures

Attention scores are dot products: score = ⟨q, k⟩. And a dot product is blind to order — shuffle the tokens and the scores shuffle with them, without ever changing value. Position therefore has to be baked into q and k themselves, and there are two classic ways to do that. You can add a position vector to each token — but then content and position occupy the same directions and the model must learn to untangle them. Or you can rotate each vector by an angle that depends on its position. That second idea is RoPE — Rotary Position Embedding (Su et al., 2021) — and it is the better choice for one beautiful reason: rotating a vector changes where it points without changing what it is.

R(p·ω) = [cos pω−sin pωsin pωcos pω] a 2×2 rotation matrix (rows: cos, −sin / sin, cos), applied to q and k in one plane

Two facts about rotations then do all the work. Rotations preserve length, so a rotated token keeps exactly the same "loudness" — position can never amplify or silence content. And rotations compose by adding angles: turn by a, then by b, and you have turned by a + b; the transpose of a rotation is simply the same rotation run backwards, Rᵀ = R(−θ). Feed those two facts into the attention score and the absolute positions cancel out of the equation:

⟨Rp q, Rp′ k⟩ = qᵀ Rpᵀ Rp′ k = qᵀ R(p′−p) k ← one rotation, by the gap
so the score depends on p′ − p and on the two tokens' content — never on where either one sits

That line is the whole trick, and it is worth reading twice. The model never tells attention "you are at position 4096"; it turns each vector by an angle proportional to 4096, and lets the difference of two turns carry the only information the score needs: how far apart these two tokens are. Zero learned parameters, no maximum sequence length, nothing to look up in a table.

One plane, though, would not be enough. A head pairs its 128 dimensions into 64 rotation planes. In FLUX.2 those planes come in four groups of 16 — one group per position axis (§4.2) — and within a group the planes run at speeds ωⱼ = θ^(−2j/32), j = 0…15: a geometric ladder from ω₀ = 1 (a full turn every 6.28 positions on that axis) down to ω₁₅ = 1/θ^(30/32) ≈ 0.0008 (barely moving at all). The score is the sum of 64 such contributions, one per plane: cos((p′−p)·ω + φ). A fast plane is a minute hand: exquisitely precise about small gaps, but it returns to the same angle every period, so gap 0 and gap 6.28 look identical to it — it aliases. A slow plane is an hour hand: never ambiguous, far too coarse to tell neighbours apart. Summed together, the ladder gives every gap its own fingerprint.

For an image model this property is not a luxury, it is the product. FLUX.2 has to accept resolutions it has never seen — anything from 512² up to 4 megapixels — and a purely relative position code extrapolates to new sequence lengths in a way that absolute position tables famously do not.

◆ Verified · the property holds in this exact implementation

I rotated a fixed query/key pair with apply_rope at several position pairs and measured the dot product. Pairs with the same gap give the same score, agreeing to within 1×10⁻⁶ — pure float32 round-off:

gap = 2 : (p=0, p=2) → 4.919082   (p=5, p=7) → 4.919081   (p=13, p=15) → 4.919082
gap = 3 : (p=0, p=3) → 6.703997   (p=5, p=8) → 6.703996

I also confirmed each produced matrix is a genuine rotation: RᵀR = I to 6×10⁻⁸ and det R = +1.000000, and that apply_rope leaves every vector's norm unchanged.

4.2 · FLUX.2's twist: four positions per token

A language model needs one position number per token. FLUX.2 needs four, because its tokens live in a 3-D volume of images stacked over a "time" axis, plus a separate index for text. Every token therefore arrives with a coordinate vector ids of shape (B, L, 4):

axisindexmeaningexample valuesRoPE dims it owns
tids[..., 0]which image in the stack — separates references from each other and from the canvas0 for canvas & text · 10, 20, 30… for refs0 – 31
hids[..., 1]row in the latent grid0 … 63 at 1 MP32 – 63
wids[..., 2]column in the latent grid0 … 63 at 1 MP64 – 95
lids[..., 3]position within the text sequence (dummy 0 for images)0 … 51196 – 127

That is exactly what axes_dim = [32, 32, 32, 32] means: each of the four axes gets 32 of the 128 head dimensions, i.e. 16 rotation planes each, 64 planes in total. It is also why Flux2.__init__ refuses to start unless sum(axes_dim) == hidden_size // num_heads — the planes have to tile the head exactly.

# image tokens: sweep (t, h, w) over the grid, l stays 0 x_coords = {"t": torch.arange(1), "h": torch.arange(h), "w": torch.arange(w), "l": torch.arange(1)} x_ids = torch.cartesian_prod(x_coords["t"], x_coords["h"], x_coords["w"], x_coords["l"]) # text tokens: t, h, w are dummies; l sweeps the sentence coords = {"t": torch.arange(1), "h": torch.arange(1), "w": torch.arange(1), "l": torch.arange(_l)} x_ids = torch.cartesian_prod(coords["t"], coords["h"], coords["w"], coords["l"]) # reference images: each one gets its own slot on the t axis, ten apart t_off = [scale + scale * t for t in torch.arange(0, len(encoded_refs))] # scale = 10
💡 Why references sit at t = 10, 20, 30 …

The canvas and the text both live at t = 0. Each reference image is pushed ten units further along the t axis. Because RoPE makes attention scores depend on coordinate differences, a reference at t = 20 is "far away" from the canvas at t = 0 in exactly the same mathematical sense that token 20 is far from token 0 in a sentence. The model therefore knows, from geometry alone, that these tokens are a different image, not a distant part of the canvas — and it can still reach them, because attention is global. One coordinate, doing the job that a special "segment embedding" would do in older architectures.
