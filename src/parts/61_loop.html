§18The denoising loop — where model.py meets the world

model.py never loops. It answers one question per call: "given this noisy image at this timestep, which way is clean?" The loop lives in sampling.py, and it is short enough to fit in your head.

guidance_vec = torch.full((img.shape[0],), guidance, device=img.device, dtype=img.dtype) for t_curr, t_prev in zip(timesteps[:-1], timesteps[1:]): t_vec = torch.full((img.shape[0],), t_curr, dtype=img.dtype, device=img.device) img_input = img img_input_ids = img_ids if img_cond_seq is not None: # reference images, if this run has any img_input = torch.cat((img_input, img_cond_seq), dim=1) img_input_ids = torch.cat((img_input_ids, img_cond_seq_ids), dim=1) pred = model(x=img_input, x_ids=img_input_ids, timesteps=t_vec, ctx=txt, ctx_ids=txt_ids, guidance=guidance_vec) if img_input_ids is not None: pred = pred[:, : img.shape[1]] # keep only the canvas rows img = img + (t_prev - t_curr) * pred # the only line that changes the image return img

This is the loop §1.2 described in words — all of it, unabbreviated. Two details the abridgement hid: zip(timesteps[:-1], timesteps[1:]) is how the loop pairs each step with the next one (no index arithmetic, and it simply stops after the last pair), and the reference tokens — when there are any — are concatenated onto the canvas before the call and sliced back off the prediction afterwards. denoise calls model(...), i.e. Flux2.forward, which always passes num_ref_tokens=0: on this path the references are ordinary image tokens (§15.4).

Read the update rule slowly, because it is the whole of rectified flow: the model predicts a velocity — the direction and speed at which the image should move — and the sampler takes one Euler step of size (t_prev − t_curr) along it. At the last step t_prev = 0, landing exactly on the clean latent, which the autoencoder then decodes into pixels. There is no noise injected anywhere: this is an ordinary differential equation being integrated, not a stochastic process.

18.1 · Which timesteps? A deterministic, shifted ladder

The step times are not evenly spaced — but they are not random either. get_schedule(num_steps, image_seq_len) (sampling.py L244–248) builds a uniform ladder torch.linspace(1, 0, num_steps + 1) and warps every rung through the shift function of §1.3, t′ = eμ / (eμ + (1/t − 1)σ) with σ = 1. Same run in, same run out — there is no sampling and no seed.

μ comes from compute_empirical_mu (sampling.py L251–266) and depends on two things. Above 4300 image tokens it is a straight line in the token count, μ = 0.00016927·L + 0.45666666. At or below 4300 tokens it interpolates between two fitted lines — one calibrated for a 10-step run, one for a 200-step run — so the step count matters too: fewer steps ⇒ larger μ ⇒ the few steps you have are pushed harder into the noisy end. The second is what the sampler keeps to itself: how far each answer is allowed to move the image. The model never sees it (§1.2). Half the steps happen above t = 0.9: the model spends its budget on the early, global structure decisions, then takes one long stride from 0.58 to 0 — one hop covering 58 % of the whole distance from noise to image, and 39 times the size of the first. ⚠ Gotcha · "logit-normal" is a training word, not an inference word

The SD3 paper samples its training timesteps from a logit-normal distribution, and that phrase is often reused for inference schedules. Nothing here is sampled or normal-distributed: the inference schedule is a fixed monotone warp of a uniform ladder, and the warp's μ is fitted empirically (per compute_empirical_mu's own name) rather than drawn. The two ideas are related — the shift concentrates steps where training concentrated probability — but they are not the same statement.

18.2 · What a step costs

Attention is quadratic in sequence length and the block matmuls are linear, so the cost of a step is dominated by token count. The counting rule, applied to the dev configuration:

Σ How these numbers are computed

FLOPs = 2 × (MACs in the blocks + MACs in the attention)

A token crossing a single block touches linear1 (6144 × 55 296) and linear2 (24 576 × 6144) = 490 733 568 MACs. A token crossing a double block touches only one of its two streams — image tokens the image weights, text tokens the text weights — and one stream costs exactly the same 490 733 568 MACs (qkv + proj + two MLP matrices). So the matmul term is 56 × L × 490 733 568, not 56 × L × 981 467 648: multiplying the double block's full parameter count by every token would count each token twice.

Attention adds 56 × 2 × L² × 6144 MACs (one q·k and one weights·v per block, over the whole joint sequence of L = image + 512 text tokens). Elementwise work — norms, SiLU, residuals — is excluded; it is under a percent.
