§15The KV cache: why it is exact, and what it costs

Everything in §9–§14 was building towards this. The claim: reference tokens produce byte-identical keys and values at every denoising step, so they can be computed once and replayed. Nothing in model.py states this as a theorem — it emerges from three design decisions that only make sense together.

15.1 · The three conditions that make it exact

conditionwhere it liveswhat it guarantees
1 · References are isolated
ref queries attend only to ref keys		causal_attn_fn
L810–811		No information from the changing canvas can reach a reference token's hidden state. Without this, step 1's references would differ from step 0's and the cache would be wrong.
2 · References are clean
ref_fixed_timestep = 0.0		forward_kv_extract
L198, L210–211		The reference modulation vector is a constant. Even though vec changes every step, ref_vec never does — so the reference tokens are transformed identically each time.
3 · Reference inputs are constant
clean VAE latents, fixed t = 10, 20, 30…		sampling.py
encode_image_refs, prc_img		The reference latents are never noised and their position IDs never move, so the input to block 0 is identical on every step.

Conditions 1–3 together give an induction: identical input + identical modulation + no leakage ⇒ identical output at block i, hence identical input at block i+1. By induction through all 56 blocks, the reference keys and values are the same tensor at every step. Caching them loses nothing.

◆ Verified · the induction holds in floating point too

Running forward_kv_extract at timestep 0.9 and again at 0.1 produced reference keys and values that were bit-identical — not merely close. Feeding the 0.9 cache into forward_kv_cached at timestep 0.5 and comparing against forward_kv_extract at 0.5 gave a maximum absolute difference of 0.000e+00 across all outputs. The optimisation is exact.

15.2 · What it costs in memory

The cache is not free: it stores two tensors per block per reference token, in the network's working precision. The formula is

Σ Memory

bytes = n_blocks × 2 (K and V) × n_ref_tokens × hidden_size × 2 (bf16)

with n_ref_tokens capped by sampling.py at 1024² pixels per reference when there is more than one, and 2024² when there is exactly one (sampling.py L56–58 — that 2024**2 is what the upstream file literally says and is almost certainly a typo for 2048²; the numbers below reproduce it faithfully). Each cap is then centre-cropped to a multiple of 16, so a single 2024²-capped square reference really contributes 2016² ÷ 256 = 15 876 tokens, and four 1024²-capped references contribute 4 × 4096 = 16 384.

The two columns are close because the token cap shrinks each reference when there are several: four references at 1024² occupy barely more cache than one at 2024².

15.3 · What it buys

Measured speedups from the upstream docs/flux2_klein_kv_cache.md:

references512 × 5121440 × 1440
1 reference image1.78× faster1.21× faster
4 reference images2.66× faster1.85× faster

The ordering is exactly what the token arithmetic predicts. At 512² the canvas is only 1024 tokens, so four references at 1024² add 4 × 4096 = 16 384 tokens to it: references are 94 % of the image-side sequence (91 % once the 512 text tokens are counted), so a cached step skips almost everything. At 1440² the canvas is 8100 tokens and the same four references are 67 % — still a majority, but a far smaller one, so the same trick saves proportionally less.

The magnitude needs one caveat. Counting tokens, a cached step at 512² should be about 12× cheaper than an uncached one: 1536 queries instead of 17 920, and 1536 tokens through the blocks instead of 17 920. The measured win is 2.66×, and the gap is honest arithmetic rather than a disappointment — a step is not only matmuls. The cache still has to be read on every step (22.55 GB of it for the dev model, which costs memory bandwidth no matter how little you compute), the queries still attend over the full 17 920-key sequence, and step 0 runs uncached by definition. So: the cache pays off precisely when you are doing reference-guided work at modest resolution, and it pays off by a factor of two-to-three, not by the factor of twelve the token count suggests.
