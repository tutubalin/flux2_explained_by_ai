§ 14The denoising loop — where model.py meets the world

model.py never loops. It answers one question per call: "given this noisy image at this timestep, which way is clean?" The loop lives in sampling.py, and it is short enough to fit in your head.

guidance_vec = torch.full((img.shape[0],), guidance, device=img.device, dtype=img.dtype) for t_curr, t_prev in zip(timesteps[:-1], timesteps[1:]): t_vec = torch.full((img.shape[0],), t_curr, dtype=img.dtype, device=img.device) img_input = img img_input_ids = img_ids if img_cond_seq is not None: # reference images, if this run has any img_input = torch.cat((img_input, img_cond_seq), dim=1) img_input_ids = torch.cat((img_input_ids, img_cond_seq_ids), dim=1) pred = model(x=img_input, x_ids=img_input_ids, timesteps=t_vec, ctx=txt, ctx_ids=txt_ids, guidance=guidance_vec) if img_input_ids is not None: pred = pred[:, : img.shape[1]] # keep only the canvas rows img = img + (t_prev - t_curr) * pred # the only line that changes the image return img

This is the unabbreviated version of the three lines quoted in §2.2. Two details the abridgement hid: zip(timesteps[:-1], timesteps[1:]) is how the loop pairs each step with the next one (no index arithmetic, and it simply stops after the last pair), and the reference tokens — when there are any — are concatenated onto the canvas before the call and sliced back off the prediction afterwards. denoise calls model(...), i.e. Flux2.forward, which always passes num_ref_tokens=0: on this path the references are ordinary image tokens (§11.4).

Read the update rule slowly, because it is the whole of rectified flow: the model predicts a velocity — the direction and speed at which the image should move — and the sampler takes one Euler step of size (t_prev − t_curr) along it. At the last step t_prev = 0, landing exactly on the clean latent, which the autoencoder then decodes into pixels. There is no noise injected anywhere: this is an ordinary differential equation being integrated, not a stochastic process.

14.1 · Which timesteps? A deterministic, shifted ladder

The step times are not evenly spaced — but they are not random either. get_schedule(num_steps, image_seq_len) (sampling.py L244–248) builds a uniform ladder torch.linspace(1, 0, num_steps + 1) and warps every rung through the shift function of §2.3, t′ = eμ / (eμ + (1/t − 1)σ) with σ = 1. Same run in, same run out — there is no sampling and no seed.

μ comes from compute_empirical_mu (sampling.py L251–266) and depends on two things. Above 4300 image tokens it is a straight line in the token count, μ = 0.00016927·L + 0.45666666. At or below 4300 tokens it interpolates between two fitted lines — one calibrated for a 10-step run, one for a 200-step run — so the step count matters too: fewer steps ⇒ larger μ ⇒ the few steps you have are pushed harder into the noisy end. For a 4096-token image (1024²) with 8 steps, μ = 2.27 and the times are

⚠ Gotcha · "logit-normal" is a training word, not an inference word

The SD3 paper samples its training timesteps from a logit-normal distribution, and that phrase is often reused for inference schedules. Nothing here is sampled or normal-distributed: the inference schedule is a fixed monotone warp of a uniform ladder, and the warp's μ is fitted empirically (per compute_empirical_mu's own name) rather than drawn. The two ideas are related — the shift concentrates steps where training concentrated probability — but they are not the same statement.

14.2 · What a step costs

Attention is quadratic in sequence length and the block matmuls are linear, so the cost of a step is dominated by token count. The counting rule, applied to the dev configuration:

Σ How these numbers are computed

FLOPs = 2 × (MACs in the blocks + MACs in the attention)

A token crossing a single block touches linear1 (6144 × 55 296) and linear2 (24 576 × 6144) = 490 733 568 MACs. A token crossing a double block touches only one of its two streams — image tokens the image weights, text tokens the text weights — and one stream costs exactly the same 490 733 568 MACs (qkv + proj + two MLP matrices). So the matmul term is 56 × L × 490 733 568, not 56 × L × 981 467 648: multiplying the double block's full parameter count by every token would count each token twice.

Attention adds 56 × 2 × L² × 6144 MACs (one q·k and one weights·v per block, over the whole joint sequence of L = image + 512 text tokens). Elementwise work — norms, SiLU, residuals — is excluded; it is under a percent.

§ 15Why the file looks like this — twelve design decisions

Reading 833 lines you meet a lot of choices that look arbitrary until you see the reason. Here they are, collected.

decisionwherethe reason
Fused projectionsL453, L459One matrix produces q, k, v and the MLP input; another consumes attention and MLP output together. Five matmuls become two, and on a GPU fewer, bigger matmuls are dramatically more efficient.
Modulation computed onceL132–13456 blocks × 3 vectors would mean 168 MLP calls per step; sharing them costs 3 and gives every block the same conditioning signal.
Parameter-free norms + adaLNL464, L470LayerNorm's own gain/bias would fight the modulation. Setting elementwise_affine=False everywhere (81 norms) makes the timestep the sole owner of scale and shift.
No biases anywhereall Linears171 linear layers, all bias=False — verifiable by grepping the file. inference The likely reason is that every linear here is followed or preceded by a normalisation whose shift is generated per token, which a constant bias adds nothing to.
fp32 for the delicate arithmeticL722–726, L741, L825, L829–832The network runs in bf16, but three things are computed in float32 and cast back: the sinusoidal frequency ladder, the RMSNorm statistics (x.float() then .to(x_dtype)) and the RoPE rotations (.float() then type_as). Note what is not in this list: LastLayer — the prediction leaves the model in the working dtype.
4-axis RoPE instead of 1-DL694–707Images are 2-D and references are separated in "time". Four rotation planes with equal dimension splits let one mechanism encode (t, h, w, l) without learned position tables.
Isolation by slicing, not by maskingL802–813No boolean mask tensor is ever built. The uncached branch makes two dense attention calls — txt+img over all keys, then ref over ref — and the cached branch needs only one, because the reference queries are gone. Same rule (FIG 11), expressed as concatenations.
8 double + 48 singleL16–17, built at L76–96depth = 8 and depth_single_blocks = 48 are config fields, consumed by the two ModuleList comprehensions in __init__. A double block costs exactly 2× a single one, so depth on the shared side is twice as cheap. FLUX.1 used 19+38; FLUX.2 moves further along that trade.
Cache as a dict of listsL260–264Plain Python structures, one entry per block in block order. No abstraction layer, no registry — the simplest thing that makes kv_cache["double_blocks"][i] obvious.
Dead code left in placeL446, L449self.hidden_dim and self.scale are never read again after __init__. They are a plain Python int and float — not parameters, not buffers — so they appear in no state_dict and cost nothing but a line each. inference They look like leftovers from a hand-written attention that scaled_dot_product_attention replaced.
Two different guard stylesL58–64, L534, L819Flux2.__init__ raises ValueError with a formatted message; DoubleStreamBlock.__init__ and rope use bare asserts (the only two in the file), which document a programming error and vanish under python -O. Same requirement, three sites, two mechanisms.
No dropout, no stochasticity—An inference-only file. Everything deterministic means the KV-cache proof of §13 holds exactly, in floating point, forever.
