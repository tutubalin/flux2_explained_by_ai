§ 5Reference images: from JPEG to tokens

FLUX.2 edits and re-uses photographs: you hand it one or more images and it keeps what is in them while it paints something new. Those photographs have to become rows of 128 numbers with addresses before the network can see them, and getting there takes six functions and one hard-coded constant that is very nearly a typo.

5.1 · The preparation chain

Every reference photo goes through the same five stages, in this order, before it is encoded. The order is not arbitrary: each stage exists to make the next one safe.

StageWhat it guarantees for the next one
to_rgb Exactly three channels. A PNG with an alpha channel, or a greyscale scan, would otherwise reach ToTensor and produce a tensor the autoencoder cannot accept.
cap_min_pixels Nothing degenerate gets through: a side shorter than 64 pixels or an aspect ratio beyond 8:1 raises ValueError immediately. This is the only place in the file that refuses work rather than doing it.
cap_pixels A ceiling on the token count, and therefore on memory and on attention cost — which grows with the square of the sequence. It scales by sqrt(k / pixels) so the aspect ratio survives, and resamples with LANCZOS.
center_crop_to_multiple_of_x(16) Both sides divisible by 16, so the 8× autoencoder and its 2×2 patchify land on whole cells. It floors to the multiple and crops from the centre, taking half the remainder off each side.
default_images_prep A float tensor in [−1, 1]: ToTensor divides by 255, then 2·x − 1 recentres it. That is the range the autoencoder was trained on.

Cap first, then crop: the cap leaves a size that is almost a multiple of 16, and the crop removes the remainder — four pixels off each side in the example above. Reverse the two and the crop would be undone by the resize.

5.2 · The budget: 2024², not 2048²

How big a photo is allowed to be depends on how many photos there are, and the two numbers in the file are not the numbers you would expect:

one reference → limit_pixels = 20242 = 4 096 576 two or more → 10242 = 1 048 576 each
⚠ A 2.33 % typo, and exactly what it costs

The single-reference budget is 2024**2. The number that would make the design round — and that matches the 2048-pixel canvas the rest of FLUX.2 is documented for — is 2048**2: 4 194 304 pixels, 97 728 more, a 2.33 % difference. Reading a four-digit year where a power of two belongs is an easy mistake, and nothing else in the file uses 2024. inference

The consequence is concrete rather than cosmetic. A 2048×2048 reference is capped to 2024×2024, which is not a multiple of 16, so it is then cropped to 2016×2016 = 126×126 = 15 876 tokens. With a 2048² budget the crop would never fire and the same photo would give 128×128 = 16 384 tokens. One transposed digit removes 508 tokens — a 3 % strip around two edges of every single-reference edit. VERIFIED by running both stages on a 2048×2048 input.

The multi-reference budget is a different shape of decision: rather than letting four photos add up to four times the tokens, each photo is held to 1024² so that the total stays near one canvas' worth. The trade-off is per-photo detail — a 2048×2048 reference loses three quarters of its pixels when it is one of four, and none when it is alone.

5.3 · Two details that only the code reveals

Encoding happens on the GPU, unconditionally. The encode call is ae.encode(img[None].cuda()) — the .cuda() is written into the line, with no device argument and no fallback. The reference path therefore cannot run on a CPU-only or Apple-silicon setup even if the rest of the pipeline could. The [None] adds the batch axis the autoencoder expects, and the [0] immediately after the call takes it back off: what encode returns is one tensor of shape (1, 128, H/16, W/16), and prc_img wants (128, h, w).

Photos are encoded one at a time. There is no batching across references — a Python for loop calls the autoencoder once per photo. With four references that is four separate encoder passes, which is also why they can be different sizes: a batch would have to be padded to a common shape.

▸ Why 16, and not 8

The autoencoder alone downsamples by 8 in each direction. FLUX.2 then folds each 2×2 block of latent cells into one token, which is another factor of 2 per side. A side length divisible by 16 is what makes both steps come out whole: 2016 → 252 latent cells → 126 tokens per side. The crop is the cheapest place to enforce that, because it happens before any of the expensive work.
