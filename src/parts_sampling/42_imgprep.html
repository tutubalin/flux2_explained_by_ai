§ 10The image-preparation chain

138 lines whose job is to make sure that whatever the user handed over — a PNG with transparency, a panorama, a 40-megapixel scan — arrives at the autoencoder as a three-channel tensor whose sides are multiples of sixteen. Five of the six functions here are four to fifteen lines long, and one of them is the only place in the file that ever says no.

10.1 · to_rgb and cap_min_pixels — normalise, then refuse

64 pixels is not an arbitrary floor. The autoencoder downsamples by 8 and the patchifier folds 2×2, so a side of 64 becomes a 4×4 grid of tokens — the smallest canvas that still has an interior. Below that the model would be asked about a picture with essentially no spatial structure. The 8:1 aspect limit is the same concern in the other direction: a 4000×400 strip is technically valid and semantically useless.

✦ Raising is better than deforming inference

Both checks raise rather than repair. The file could have centre-cropped a 10:1 panorama down to 8:1, and it already owns a function that does exactly that kind of crop — but a silent crop would change what the user asked for, while an exception makes the caller decide. Every other function in this chain fixes what it can; this one is the only one that reports instead.

Worked example, verified by running the arithmetic of the function: a 3000×2000 photograph has 6 000 000 pixels, so with a 1024² budget the scale is sqrt(1 048 576 / 6 000 000) = 0.41805, the new sides are int(1254.14) = 1254 and int(836.09) = 836, and the result is 1254×836 = 1 048 344 pixels — 232 under the budget, still exactly 3:2, and about to lose six columns and four rows to the crop that follows, ending as 1248×832 = 4 056 tokens.

10.3 · center_crop_to_multiple_of_x — making the grid come out whole

The asymmetry in the last point is small enough to be worth stating precisely, because it is the only place in the file where a picture is not treated symmetrically: with a remainder of 9 pixels on a side, 4 are removed from the left and 5 from the right. For the 2024² reference of §5 the remainder is 8, so it is exactly centred — four pixels off each side.

10.4 · default_images_prep and default_prep — the chain assembled

▸ Why the order cap → crop cannot be swapped

Cropping to a multiple of 16 first and then resizing would undo the crop: cap_pixels multiplies the sides by an irrational scale factor and truncates, so its output is essentially never a multiple of 16. Capping first and cropping second means the crop only ever has to remove the few pixels the cap left over — at most 15 per side, and in the 2024² case exactly 8.

10.5 · concatenate_images — the one that is not part of sampling

Nothing in the sampling path calls this. Its only caller in the repository is text_encoder.py, which uses it when prompt upsampling is on: several reference photographs are pasted side by side into one image, capped to 768², and shown to a vision-language model that is asked to write a better prompt. That is why it lives here at all — this file is where the repository keeps its image utilities, whether or not the sampler uses them.

✦ Three pixel budgets, one function

cap_pixels is the only function in the file that is called from outside the sampling path with a different budget than the sampler uses: 2024² for one reference, 1024² for several, 768² for the language model. Passing the budget as an argument rather than a module constant is what allows that, and it is the reason the number 2024 lives in encode_image_refs instead of here.

§ 11vanilla_guidance — the function nothing calls

Four lines, wedged between two loops, implementing the textbook version of the arithmetic that denoise_cfg performs inline. It is correct, it is never used, and reading it tells you something about how this file grew.

Compare it with the two lines that denoise_cfg actually executes:

vanilla_guidance: x_u, x_c = x.chunk(2); x = x_u + cfg_val·(x_c − x_u)
denoise_cfg: pred_uncond, pred_cond = pred.chunk(2); pred = pred_uncond + guidance·(pred_cond − pred_uncond)

Same chunk(2), same order of halves, same formula. The only differences are the variable names and that the loop's version does not need to return anything.

◆ Nothing in the repository calls it

Checked by grepping every Python file in black-forest-labs/flux2: vanilla_guidance appears exactly once, on the line that defines it. scripts/cli.py imports eight names from this module — batched_prc_img, batched_prc_txt, denoise, denoise_cached, denoise_cfg, encode_image_refs, get_schedule, scatter_ids — and text_encoder.py imports two more, cap_pixels and concatenate_images. This one is in neither list, and no function in this file calls it either.

What it is, then, is a reference implementation: the formula written down in the cleanest possible form, next to the loop that uses it, for anyone reading the file who wants to check that the inline version says what classifier-free guidance is supposed to say. inference It costs nothing to keep — four lines, no state — and it documents the convention that the first half of a doubled batch is the unconditional one, which is the single detail a reader would otherwise have to infer from the caller's torch.cat([ctx_empty, ctx_prompt], dim=0).
