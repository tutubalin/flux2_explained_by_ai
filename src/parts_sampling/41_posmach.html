Part 3
The small parts

Sixteen of the twenty-one functions, in dependency order: the machinery that writes and reads token addresses, and the chain that turns a photograph into a tensor. Each one is short enough to read in full, and each is quoted here line by line from the real file.

§ 9The position machinery

Six functions and three constants, 92 lines, one job: give every token four numbers, and be able to undo it. Nothing here touches the network. Read this chapter and the _ids arguments in every loop signature stop being mysterious.

9.1 · compress_time — renumbering the planes

The function exists for one reason, and it is a memory reason. If three reference photographs sit at t = 10, 20 and 30, a volume indexed by the raw coordinate would need 31 planes, of which 28 are empty. Compressed first, the same information needs four planes. compress_time is called from exactly one place — scatter_ids, §9.2 — and only ever on the way out of the loop, when tokens have to become a picture again.

▸ The trick is a lookup table, not a search

Writing "0, 1, 2, 3…" at the positions that occur and then indexing with the original ids is the standard way to densify a set of small integers on a GPU. It costs one table of size max + 1 and two gather operations, and it has no Python loop in it — which matters, because this runs on tensors that can be tens of thousands of elements long.

9.2 · scatter_ids — putting the tokens back into a picture

⚠ Two loose ends in this function

The fourth axis is never read. Lines 32–34 take pos[:, 0], pos[:, 1] and pos[:, 2] — t, h, w. The l axis is ignored, which is harmless for a canvas (every canvas token has l = 0) and would be very harmful for text: 512 prompt tokens differing only in l would all be scattered into the same cell. scatter_ids is only ever called on canvas ids, after the loop.

t_coords is built and thrown away. Line 29 creates the list, line 48 appends the distinct plane indices of each sample to it, and line 49 returns only x_list. It is dead in the shipped file — the signature of a version that once told the caller which planes it had reconstructed, which would matter if a batch mixed canvases and references. inference

9.3 · prc_txt and prc_img — writing the addresses

The two functions are mirror images, and the mirroring is the point. Text spreads along l and is pinned at the origin of h and w; images spread over h and w and are pinned at l = 0. Both use the same four-axis dictionary and the same cartesian_prod, so the network sees one homogeneous (N, 4) id tensor no matter which family a token belongs to.

∑ Why "last axis fastest" is load-bearing

torch.cartesian_prod(t, h, w, l) returns rows in the order of an odometer whose rightmost dial spins fastest. For an image with a single t and a single l, that order is (h₀w₀), (h₀w₁), …, (h₁w₀), … — precisely what rearrange(x, "c h w -> (h w) c") produces, because einops' fused (h w) axis is also row-major. If either one had been column-major, every token would carry the address of a different patch, and the model would still run perfectly while producing scrambled images — the kind of bug no shape check ever catches.

9.4 · The two wrappers — batch and list

Two wrappers rather than four functions is a small decision with a real payoff: the address logic is written once per modality, and the "collection shape" is a separate axis. It also makes the difference between the canvas and the references explicit — torch.stack versus list is exactly the difference between "samples that must match" and "samples that need not".
